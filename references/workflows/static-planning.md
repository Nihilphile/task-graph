# 一次性详细规划

目标是让空白上下文的执行者只凭项目位置、CLI 和 task ID 找到施工所需信息。本模式默认 static；动态骨架与逐步 refine 是另一种规划选择。

## 从确认的目标到可验收切片

读取用户指定的需求全文及必要代码，区分事实、已确认决定和待查假设。复用已有探索；文档中的建议作为输入，执行范围来自用户授权。

每项实现任务交付一条窄而完整的可观察行为（tracer bullet），覆盖所需各层；先打通最小路径，再加变化和边界。前置整理或调查应有可检查产物。依赖表示确实必须等待的交付，共享文件本身不等于业务依赖；必须串行时解释原因。父子表达归属，依赖表达先后。

机械迁移可采用 expand–migrate–contract：兼容新旧形式、分批迁移、最后移除旧形式。中间批次无法独立保持通过时，写清共同集成位置、最终验收及每批验证边界。

检查每项已确认需求有任务承接或明确排除理由。用户已授权建图则继续写入；仅要求讨论时先给可审阅拆分。尚未决定的方案保留为待解决输入。

## 任务要求是唯一派工正文

content 写明目标、范围、已确认约束、输入定位、验证方式、验收责任和交付位置；较长权威资料给路径与章节/符号、版本及用途。正文不重复维护 CLI 管理的 ID、状态和依赖。

主控把共享约定登记为 contract，执行者同步契约变化，并按需提供 reference 代码入口。父任务与相邻任务的正文不会自动继承。首次写要求或有上下文缺口时读 [任务上下文设计](../../skills/to-task/references/task-context.md)。

独立审查的 RR 描述可操作的检查条件；实现任务自身验证、独立验收子任务、auto-review 的责任按实际需要分配，避免重复验收。

## 落图与交接

准备要求文件和带稳定 key 的批量计划，按 [创建计划](../operations/planning.md) 写入并保存 key→ID 回执。已有 ID 用 revise 维护，新工作才创建新 key。复杂父子关系读 [子图与完成点](../operations/relationships.md)。示例见 [plan.json](../../skills/to-task/assets/example/plan.json)。

完成时应有要求入口、真实任务 ID、依赖和 HTML，关键引用在接手环境可读；validate 只验证结构。交接按 [主控协作](controller.md)。本 Skill 默认完成建图和交接，用户同时授权实施时继续施工。
