# 主控协作

## 派工

确认要求、前置产物和验证入口可用；ready / validate 只证明结构条件，动态任务仍须评估并 refine。多任务施工按[任务划分与并行安排](dynamic-planning.md#任务划分与并行安排)决定顺序及责任。

给执行者项目/checkout、CLI、任务地址和 [task-take](../../skills/task-take/SKILL.md) 入口，要求正文绑定到任务。同一次 start 由一方登记实际执行会话；主控已 start 时告知执行者从 show 接续。claim 不启动代理。

共享规则绑定同一 [contract](../operations/contracts.md)，要求只补本任务范围、验收及共享资源安排；前置代码导航使用 reference 条目。需要独立留档的已定决策用该手册的 decision record 一次登记。执行者自行接手和交付，主控不另设例行汇报、开工或 complete 批准门槛。

共享验证优先依靠稳定契约、模块边界和明确的文件所有权组织；遇到实际共享写入或构建冲突时，只协调受影响的任务和时段。日常测试直接使用项目已有入口，不默认全员停写、逐次审批、主控代跑或测试前强制提交。快照、队列和独立 worktree 仅在具体问题需要时采用，不为协调便利额外建设流程；既定验收对象的稳定要求限于其实际输入范围。

## 根据交付推进

读报告与证据，满足要求则推进后继，否则安排修复、调查或独立审查。reference 不能单方面改变已确认约定；范围变化须协调正在执行的任务。

父任务承担统筹还是施工须事先明确，完成目标满足后仍需负责人显式 complete。重审同一交付见[审查控制](../operations/review-control.md)，修改交付则按[接手修复](../operations/execution.md)处理。

## 通知与交接

需要结果唤回时按[订阅](../operations/watch.md)登记自己的 Desktop UUID；收到后核对当前状态与本轮证据，通知不自动放行后继。

交接给出图与任务地址、当前判断、未决问题及 HTML 入口，已有材料直接引用。GitHub 发布见[同步](../github-sync.md)。
