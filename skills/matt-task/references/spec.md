# Spec 阶段

读取已讨论的需求、Grill 结论、现有 spec、必要代码事实及相关 ADR/GLOSSARY，综合已有决定，不重新采访。用户给出的路径或外部来源读完整相关内容；复用已有探索，不能把实现建议或原型猜测当成已批准范围。

## 内容与可施工性

spec 应覆盖以下内容，标题可沿项目布局组织：

- 用户面对的问题与方案带来的可观察变化。
- 编号的用户故事或行为要求，覆盖正常路径、实际需要的变化和边界，供任务映射；无需为凑数量扩展需求。
- 已确认实施决定：模块职责、接口语义、数据约束及有依据的技术选择。
- 测试决定：公开 seam、应观察的行为、验收条件、可复用验证方式与必要环境。
- 排除范围、必要来源、尚未决定的事项及其影响。

优先已有且足够高的公开 seam，以外部行为判断正确性。已确认的 seam 直接保存并继承；实质新选择用具体方案指出缺口，不能通过填模板代替用户决定。普通内部实现细节留给执行者。

spec 以行为与约定为主，当前代码定位留在任务输入或 reference。原型中精确表达已定决定的状态机/类型形状可以引用或保存必要片段，注明来源与适用性。

未决选择影响所有切片时，交付标明未完成的草稿并说明缺口，不宣称完整可施工。只影响局部时明确该局部边界，不阻止无关的已确认范围被规划。

## 保存为一个 contract

首次接入 CLI 时读 [定位与保存规则](task-graph.md)。spec 是项目内一份权威 Markdown 文件，contract 登记同一文件，不再复制一份正文到其他 tracker 或要求文件。

已有 spec contract 时使用原 ID 和权威路径；已有本地 spec 文档时直接登记该文件。外部文档需要导入时明确采用的版本和本地权威入口，不维护两份同时可改的 spec。默认一个 spec contract，真正需要跨功能复用的接口约定才单独登记。

```text
CLI contract add --graph <实际图ID> --title "<功能> spec" --file "<项目相对spec路径>" --cwd "<图项目>" --json
CLI 'contract[<实际contract ID>]' show --cwd "<图项目>" --json
```

记录 contract 返回的 ID 和正文路径。创建回执不确定时先查询 contract list，按图归属、标题和文件核对；contract add 无稳定 key，不能直接重试产生副本。仅生成 spec 时可以创建必要的项目/图容器，不创建施工任务或伪造“spec 已实施”的完成记录。

修改已有 spec 通过 `contract update --file "<更新稿路径>"` 写回原权威文件，或直接编辑原文件后 validate/build。更新仍使用原 ID；更新稿不是第二个权威来源。若已有消费者，先检查受影响任务和实际执行状态，协调范围/判据的实质变化；未协调修改不能依赖工具自动撤销放行。

contract 表示当前约定，无 done/ready 状态。需要等待某个能力实现时使用任务依赖。历史版本从 Git 或既有材料快照定位；未提交且未快照的旧文本不会由 contract 自动留成历史版本。

## 阶段交付

给出 spec 文件、contract ID、已确认测试边界与未决项。只生成 spec 的请求到此结束；准备建图时把同一 contract 交给 Tickets 阶段，不重新生成一份 spec。
